# 推送通知：已决定不做

这个文档原来写的是 Bark / ntfy 的配置方法。**现在是明确的取舍记录**，不是待办。

## 结论

不做推送。锁屏状态下收不到 DSH 的提问提醒。

## 为什么

- 唯一的可靠唤醒通道是第三方推送（Bark / ntfy），意味着**提问内容要经过第三方服务器**
- 而这个 App 的前提是端到端加密：手机和电脑之间不经过任何第三方
- 为一个提醒功能引入这条出网路径，等于把整个隐私模型撕开一个口子
- 实际使用里，DSH 的提问大多发生在你主动发起任务之后的几分钟内，那时 App 通常就在前台

## 现在锁屏会发生什么

| 场景 | 表现 |
|---|---|
| 锁屏时 DSH 提问，几分钟内解锁回 App（进程还活着） | ✅ 能看到卡片（SSE 断线重连 + 帧重放） |
| 锁屏期间 App 被系统回收，重开 | ✅ 能看到卡片（`/v1/ask/pending`，桥从帧流跟踪未答提问） |
| 一直锁屏不碰手机 | ❌ 不会有任何提醒，任务就停在那里 |

第三条是明确接受的行为。要处理长任务，就在电脑旁边，或者睡前别丢一个需要授权的任务。

## 如果以后改主意

桥里的接口是现成的，配置 `notify.kind` 非空就会出网：

```yaml
dsh-phone-bridge:
  notify:
    kind: bark          # 或 ntfy
    barkKey: YOUR_KEY
```

出网范围、能拿到什么、拿不到什么，见 `docs/安全须知与免责声明.md`。
